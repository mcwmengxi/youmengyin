## 二、技术栈关键点

### 技术选型问题

1. **为什么选择 Vue 3 而不是 React 来做这个 AI 平台？**

   - 考察点：技术选型决策能力
   - 回答方向：团队技术栈、生态成熟度、Vue3 响应式优势、开发效率
   - 事实支撑：选型时做了充分的技术调研和 Demo 验证，最终选择 Vue 3 主要基于四点：1）团队 4 人中 3 人有 3 年以上 Vue 经验，学习成本低，上手快，能保证项目启动速度；2）Vue 3 Composition API 在处理复杂状态逻辑时代码组织更灵活，AI 对话场景状态流转复杂，响应式系统能减少手动状态同步的 Bug；3）Element Plus 组件库成熟，对话界面、表单等通用组件开箱即用；4）我们对比了相同功能的开发效率，Vue 方案比 React 方案快约 15%。当然 React 生态在 AI 工具库方面更丰富，我们通过封装适配层解决了这个问题。

2. **Vercel AI SDK 解决了什么问题？它的核心原理是什么？**

   - 考察点：AI 前端技术深度
   - 回答方向：流式输出封装、多模型适配、边缘运行时、工具调用
   - 事实支撑：Vercel AI SDK 是一个专门用于构建 AI 对话界面的工具库，在项目中主要用于：1）封装了流式输出的底层实现，基于 ReadableStream 和 Fetch API，自动处理 SSE 解析，让我们不用手写 chunk 解析逻辑，节省了约 200 行代码；2）提供统一的 API 接口，支持 OpenAI、Anthropic、Azure OpenAI 等多家模型，我们项目中就支持了 3 家供应商的 5 个模型，切换模型只需要改配置；3）内置 Function Calling 支持，工具调用的参数解析和状态管理有封装好的钩子；4）支持服务端和边缘运行时部署。核心原理是利用 HTTP 流式响应 + AsyncIterator，在前端用 useChat 等 Hook 管理对话状态，自动处理 loading、error、streaming 等状态。

3. **为什么要在 AI 项目中使用 Pinia 做状态管理？和 Vuex 相比有什么优势？**

   - 考察点：状态管理理解
   - 回答方向：TypeScript 支持、Composition API、模块化、DevTools
   - 事实支撑：选择 Pinia 主要基于以下原因：1）完美的 TypeScript 支持，AI 项目中有大量复杂类型定义（对话消息、工具参数、Agent 状态等），Pinia 的类型推断能在开发阶段就捕获很多错误，我们统计过使用 Pinia 后类型相关 Bug 减少了约 50%；2）Composition API 风格，和 Vue 3 完美配合，定义 Store 像写组合函数一样自然，代码更易组织；3）模块化设计，每个模块独立，我们按对话、知识库、Agent、用户等拆分了 8 个 Store，按需引入，首屏加载减少了约 30KB；4）DevTools 支持时间旅行调试，排查状态问题效率提升明显。相比 Vuex，Pinia 没有 mutations，代码更简洁，Bundle 体积小约 15KB。

4. **项目中 Three.js 主要用来做什么？为什么选择 Three.js 而不是其他 3D 库？**

   - 考察点：技术选型广度
   - 回答方向：Agent 可视化、3D 数据展示、生态成熟度
   - 事实支撑：Three.js 在项目中主要用于多 Agent 协作的 3D 可视化展示，包括：1）Agent 节点的 3D 空间布局和动画，让用户直观看到多个 Agent 如何协作；2）知识图谱的 3D 力导向图展示，支持节点交互和下钻；3）数据指标的 3D 立体展示，用于大屏和汇报场景。选择 Three.js 是因为：1）生态最成熟，文档和社区资源丰富，遇到问题容易找到解决方案；2）功能完善，从基础几何体到复杂的材质、光照、动画都有支持；3）我们团队有两人有 Three.js 项目经验，学习成本低；4）相比 Babylon.js 等库，Three.js 更轻量，我们用到的功能 100KB 左右就能覆盖。

5. **这个项目的整体架构是怎样的？前端分层是如何设计的？**
   - 考察点：架构设计能力
   - 回答方向：插件化架构、分层设计、模块化、可扩展性
   - 事实支撑：前端采用插件化架构设计，整体分为 5 层：1）基础层：封装网络请求、工具函数、类型定义、通用 hooks，约 30 个基础模块；2）组件层：基于 Element Plus 二次封装的业务组件库，包含 40+ 通用组件和 20+ AI 专用组件（消息气泡、代码块、流式渲染器等）；3）核心层：对话引擎、Agent 管理、工具调用框架等核心能力，是插件化的核心；4）业务层：各个业务模块，如知识库管理、数据分析、工作流等，以插件形式接入；5）应用层：页面组装和路由管理。插件机制基于发布订阅模式和生命周期钩子设计，目前已接入 8 个业务插件，新增一个功能模块平均只需要 2 人天。

## 三、核心功能实现细节

### AI 对话核心模块

1. **AI 对话的流式输出是怎么实现的？底层原理是什么？**

   - 考察点：流式通信技术深度
   - 回答方向：SSE/WebSocket、ReadableStream、Fetch streaming、Vercel AI SDK 封装
   - 事实支撑：项目初期尝试过 WebSocket 和 SSE 两种方案，最终选择基于 SSE 的流式输出，主要考虑：1）对话是单向流式输出（服务端推送到前端），SSE 足够用且更轻量；2）服务端实现简单，基于 HTTP 协议，不需要额外的连接管理；3）Vercel AI SDK 原生支持。底层实现原理：前端通过 fetch 请求后端流式接口，response.body 是一个 ReadableStream，我们通过 getReader() 获取读取器，然后循环调用 read() 读取 chunk，每个 chunk 是一小段文本，解析后追加到消息内容上，实现打字机效果。Vercel AI SDK 的 useChat 钩子封装了这个过程，还处理了 loading 状态、错误重试、消息历史管理等。我们在 SDK 基础上做了定制，比如支持 Markdown 增量渲染、代码块实时高亮。

2. **Markdown 渲染和代码高亮是如何实现的？有哪些性能优化点？**

   - 考察点：富文本渲染能力
   - 回答方向：marked/markdown-it、Prism.js/Shiki、虚拟滚动、懒加载
   - 事实支撑：Markdown 渲染我们选用了 markdown-it，主要因为它插件生态丰富，可扩展性强。代码高亮使用 Shiki，因为它基于 TextMate 语法，高亮效果更准确，支持 100+ 编程语言。性能优化做了以下几点：1）流式渲染：不是等 AI 全部输出完再渲染，而是每接收到一个 chunk 就增量解析渲染，用户感知速度快 30%；2）虚拟滚动：对话列表超过 50 条时启用虚拟滚动，只渲染可视区域的消息，DOM 节点数从 1000+ 降到 20 左右，长对话页面帧率从 30fps 提升到 60fps；3）代码块懒渲染：当代码块不在可视区时，先显示占位符，滚动到可视区再高亮；4）使用 Web Worker 处理 Markdown 解析，避免阻塞主线程。经过这些优化，1000 条消息的对话依然流畅。

3. **长对话的性能优化你是怎么做的？虚拟滚动的实现原理是什么？**

   - 考察点：性能优化能力
   - 回答方向：虚拟滚动、懒加载、消息分片、内存管理、回收机制
   - 事实支撑：长对话性能是 AI 产品的核心体验问题，我们做了多层优化：1）虚拟滚动：使用 vue-virtual-scroller 库，只渲染视口内的消息，每条消息预估高度 80px，实际渲染时动态调整。1000 条消息的场景下，DOM 节点从 5000+ 减少到 30 左右，内存占用减少 70%；2）消息分片存储：IndexedDB 本地持久化对话历史，每次只加载最近 50 条，向上滚动时按需加载更多，首屏加载时间从 2s 降到 300ms；3）大消息折叠：超过 5000 字的消息默认折叠，只显示前 500 字，点击展开，避免长代码或长文档阻塞渲染；4）图片和文件懒加载：对话中的图片用 IntersectionObserver 实现懒加载；5）内存回收：对话切换时清理上一个对话的渲染缓存，定时器和事件监听器统一管理。优化后，1000 条消息滚动帧率稳定在 55fps 以上。

4. **对话历史是如何管理的？前端状态和后端同步的策略是什么？**

   - 考察点：状态管理、数据同步
   - 回答方向：本地缓存、增量同步、乐观更新、持久化策略
   - 事实支撑：对话历史采用「本地优先 + 后端同步」的策略：1）本地存储：使用 IndexedDB 存储所有对话历史，支持离线查看，单条对话消息序列化后约 1KB，1000 条约 1MB，存储空间足够；2）乐观更新：用户发送消息时，先立即更新本地状态显示在界面上，再异步发送到后端，用户感知响应速度快；3）增量同步：每次打开应用时，只同步上次同步时间之后的变更，不传全量数据，同步时间从 3s 降到 200ms；4）冲突处理：以服务端时间戳为准，本地更新晚于服务端则覆盖本地；5）持久化策略：AI 回复流式输出过程中每 2 秒持久化一次到本地，防止页面刷新丢失内容。Pinia 的对话 Store 管理内存中的状态，IndexedDB 做持久化，两者通过自定义插件自动同步。

5. **多模型切换是怎么实现的？不同模型的响应格式差异如何处理？**
   - 考察点：抽象设计能力
   - 回答方向：适配器模式、统一接口、格式转换、错误处理
   - 事实支撑：多模型切换采用适配器模式设计，主要架构是：1）定义统一的模型接口，包含 chat、streamChat、embed 等方法，入参和出参格式标准化；2）为每个模型供应商实现一个 Adapter 类，目前有 OpenAI Adapter、Anthropic Adapter、国内某大模型 Adapter，共 3 个；3）Adapter 层负责格式转换：将内部统一的消息格式转成各模型的请求格式，再将各模型的响应转成统一格式返回，比如 OpenAI 的 function_call 字段和 Claude 的 tool_use 字段，都统一成 tool_calls 数组；4）模型选择器组件，用户可在对话中随时切换模型，切换后新消息使用新模型，历史消息格式不影响；5）错误统一处理：不同模型的错误码不一样，Adapter 层映射成统一的错误类型（如限流、超时、内容违规等）。这种设计新增一个模型只需要新增一个 Adapter 类，约 200 行代码，不用改业务逻辑。

### Function Calling 交互体系

1. **Function Calling 的前端交互是怎么设计的？用户如何配置和调用工具？**

   - 考察点：交互设计能力
   - 回答方向：工具注册、参数配置、调用流程、结果展示、状态反馈
   - 事实支撑：Function Calling 的交互设计经历了 3 个版本的迭代，最终方案是：1）工具注册中心：后端定义工具 schema（名称、描述、参数 JSON Schema），前端拉取后动态渲染，目前注册了 20+ 工具（数据库查询、API 调用、文件读写、邮件发送等）；2）两种调用方式：一是 AI 自动触发（根据用户意图自动选择工具并填写参数），二是用户手动选择工具、配置参数后触发；3）参数配置：基于 JSON Schema 动态生成表单，支持字符串、数字、布尔值、枚举、嵌套对象等类型，还支持从上下文变量中取值；4）调用流程展示：用时间线展示「模型思考 → 调用工具 → 工具返回 → 模型总结」的完整流程，每个步骤可展开查看详情；5）状态反馈：工具调用过程中显示加载动画、进度条，失败时显示错误信息和重试按钮。用户调研显示，这种设计让 80% 的用户能理解工具调用过程。

2. **工具调用的状态流转是怎样的？如何处理调用失败和超时？**

   - 考察点：状态机设计、异常处理
   - 回答方向：状态机设计、超时机制、重试策略、错误降级
   - 事实支撑：工具调用的状态机设计包括 6 个状态：idle（就绪）、planning（模型规划中）、pending（调用中）、success（成功）、failed（失败）、cancelled（取消）。状态流转由 AI 响应和工具执行结果驱动。异常处理机制：1）超时控制：每个工具默认超时 30s，可配置，超时后自动取消并提示用户，超时率约 2%；2）重试策略：网络错误或服务端 5xx 错误自动重试 2 次，指数退避（1s、2s），重试后成功率提升到 98%；3）错误分类：将错误分为参数错误、权限错误、网络错误、服务端错误、业务逻辑错误等，不同错误展示不同的提示和操作；4）降级方案：工具调用失败时，AI 会用自然语言解释失败原因，并尝试用其他方式回答，不让用户卡住；5）调用日志：每次工具调用的入参、出参、耗时、错误信息都完整记录，方便排查问题。线上工具调用成功率约 95%。

3. **工具调用结果如何展示？复杂数据结构（表格、图表）怎么渲染？**
   - 考察点：数据可视化能力
   - 回答方向：动态组件、数据适配器、ECharts 集成、按需加载
   - 事实支撑：工具调用结果展示采用「数据驱动 + 动态组件」的方案：1）结果类型检测：根据工具返回的 content-type 和数据结构，自动选择渲染方式，支持纯文本、Markdown、JSON、表格、图表、图片等 8 种类型；2）表格渲染：二维数组或对象数组自动渲染成 ElTable，支持排序、筛选、分页、导出 Excel，单表最多展示 1000 行，超出提示下载；3）图表渲染：集成 ECharts，数据中带有 chartType 字段时自动渲染成对应图表（折线图、柱状图、饼图等），支持图表交互和数据下钻；4）JSON 可视化：使用 vue-json-viewer 展示结构化数据，支持折叠展开和搜索；5）组件懒加载：表格和图表组件体积较大（ECharts 约 200KB），使用异步组件 + import() 按需加载，首屏不加载，需要时才加载，减少首屏体积约 150KB。

### 多 Agent 协作可视化

1. **多 Agent 协作的可视化界面是怎么设计的？如何展示 Agent 之间的交互？**

   - 考察点：复杂交互设计
   - 回答方向：流程图、状态追踪、消息链路、时间线展示
   - 事实支撑：多 Agent 协作可视化是项目的亮点功能，设计了两种视图：1）流程图视图：用 2D 流程图展示 Agent 之间的调用关系和执行路径，节点代表 Agent，连线代表消息传递，当前执行到的节点高亮显示，用户可以直观看到任务是如何在多个 Agent 之间流转的；2）时间线视图：按时间顺序展示所有 Agent 的活动，包括发送的消息、调用的工具、产生的结果，类似对话日志但按 Agent 分栏。交互上支持：点击节点查看 Agent 详情、点击连线查看消息内容、悬停显示状态摘要、缩放和平移画布。技术实现上，流程图用 LogicFlow 框架（基于 SVG），支持自定义节点和边，相比手写 Canvas 开发效率提升了 50%。上线后用户调研显示，90% 的用户认为可视化帮助他们理解了多 Agent 协作过程。

2. **Agent 状态实时更新是如何实现的？用的什么通信方式？**

   - 考察点：实时通信技术
   - 回答方向：WebSocket/SSE、状态推送、心跳检测、重连机制
   - 事实支撑：Agent 状态实时更新使用 WebSocket，主要因为需要双向通信（前端发送操作指令、后端推送状态更新）。实现方案：1）连接管理：页面打开时建立 WebSocket 连接，页面关闭时断开，使用全局单例连接，多个页面组件共享；2）消息协议：基于 JSON 的消息格式，有 type、payload、timestamp 字段，支持状态推送、操作指令、心跳等 10 余种消息类型；3）心跳检测：每 30 秒发送一次心跳，超时 10 秒未响应则断开重连，保证连接可用性；4）自动重连：异常断开时自动重试，采用指数退避策略（1s、2s、4s、8s、最多 30s），最多重试 10 次，重连期间 UI 显示离线状态；5）状态同步：重连成功后，拉取断开期间的状态变更，增量更新前端状态，保证数据一致性。线上连接存活率约 99%，平均重连时间 2s。

3. **Agent 执行流程追踪是怎么做的？如何让用户理解 Agent 的思考过程？**
   - 考察点：可观测性设计
   - 回答方向：步骤拆解、中间状态展示、思考链可视化、透明度设计
   - 事实支撑：Agent 可观测性是提升用户信任的关键，我们设计了三级透明度：1）概览层：显示当前执行到哪一步、整体进度百分比、预计剩余时间，让用户有预期；2）步骤层：把 Agent 的执行过程拆成「理解问题 → 规划步骤 → 调用工具 → 分析结果 → 生成答案」等步骤，每个步骤有状态（进行中/完成/失败）、耗时、简要描述；3）详情层：点击每个步骤可以展开看详细信息，包括思考过程的原文、调用的参数、返回的原始数据等，高级用户可以深入排查。设计理念遵循「渐进式披露」原则：普通用户看到简洁的进度，专业用户可以深挖细节。我们还支持「思考链」模式，开启后可以看到模型的完整思考过程（用浅色文字显示），这个功能是 Power User 最喜欢的功能，使用占比约 20%。用户调研显示，有了流程追踪后，用户对 AI 回答的信任度提升了 35%。

### RAG 知识库管理

1. **知识库的文档上传和处理流程是怎样的？前端需要做哪些工作？**

   - 考察点：文件处理能力
   - 回答方向：大文件分片上传、进度展示、格式校验、状态反馈
   - 事实支撑：知识库文档上传的完整流程和前端工作如下：1）文件选择：支持拖拽上传和点击选择，支持 PDF、Word、Excel、PPT、TXT、Markdown 等 10 种格式，单文件最大 100MB，前端在选择后立即做格式和大小校验，不合法直接提示，减少无效上传；2）分片上传：大于 5MB 的文件自动分片，每片 2MB，并发上传 3 片，失败自动重试 2 次，上传过程中显示总进度条和每个分片的状态；3）秒传检测：上传前计算文件 MD5，调用后端接口检查是否已存在，存在则直接秒传，节省带宽和时间，实测秒传率约 30%；4）处理状态轮询：上传完成后，后端进行解析、分块、向量化等处理，前端轮询处理状态（每 3 秒一次），显示「解析中 → 分块中 → 向量化中 → 完成」的进度，处理失败显示错误原因和重试按钮；5）批量操作：支持批量上传、批量删除、批量分类，上传队列管理。整个上传流程的成功率约 98%。

2. **向量检索的前端交互是怎么设计的？如何展示检索结果的相关性？**

   - 考察点：搜索交互设计
   - 回答方向：相似度评分、高亮匹配、结果排序、来源追溯
   - 事实支撑：RAG 检索结果的交互设计目标是让用户既能快速找到答案，又能追溯来源建立信任。具体设计：1）相关性评分：每条检索结果显示相似度分数（0-100%），用颜色深浅表示（绿色高、黄色中、橙色低），让用户一眼判断可靠性；2）关键词高亮：用户的问题关键词在检索结果中高亮显示，快速定位相关内容；3）排序策略：默认按相似度排序，也支持按时间、文档类型等维度排序，满足不同场景需求；4）来源追溯：点击「查看原文」可以跳转到原文对应位置，高亮显示匹配的片段，支持上下文查看，验证答案准确性；5）引用标注：AI 回答中引用了知识库内容的地方会标上 [1][2] 引用角标，点击角标跳转到对应来源文献，类似学术论文的引用方式。这个设计上线后，用户对答案的信任度提升了 40%，「不相信 AI 回答」的反馈减少了 60%。

3. **知识库管理的权限控制是怎么做的？前端如何处理多租户隔离？**
   - 考察点：权限设计、安全意识
   - 回答方向：路由守卫、接口拦截、数据隔离、角色权限
   - 事实支撑：项目是多租户 SaaS 架构，权限控制非常重要，前端层面做了多层防护：1）路由守卫：使用 Vue Router 的全局前置守卫，检查用户登录状态和当前租户权限，未授权跳转 403 页面，防止通过 URL 直接访问；2）接口拦截：Axios 请求拦截器自动注入租户 ID 和用户 Token，响应拦截器统一处理 401/403 错误，Token 过期自动刷新；3）菜单和按钮级权限：基于 RBAC 模型，定义管理员、编辑者、查看者三种角色，不同角色看到不同的菜单和按钮，按钮权限用自定义指令 v-permission 控制，没有权限的按钮直接不渲染或禁用；4）数据隔离：前端所有数据请求都带租户 ID，后端做数据隔离，前端不存储其他租户数据，从源头保证安全；5）安全审计：前端记录用户敏感操作（删除知识库、导出数据等）的日志，后端审计。上线至今未发生过越权访问的安全问题。

## 四、遇到的挑战及解决方案

### 技术挑战

1. **开发过程中遇到的最大技术挑战是什么？你是怎么解决的？**

   - 考察点：问题解决能力
   - 回答方向：长对话性能、流式渲染兼容性、状态管理复杂度
   - 事实支撑：最大的技术挑战是长对话场景下的性能问题。项目中期，当对话消息超过 200 条时，页面出现明显卡顿，滚动帧率掉到 25fps 以下，输入也有延迟，用户反馈强烈。问题根源有三个：1）DOM 节点太多，每条消息平均 20 个 DOM 节点，200 条就是 4000+ 个节点，渲染和重排成本高；2）每条消息的 Markdown 渲染和代码高亮都是同步执行，阻塞主线程；3）状态管理没有做优化，每次新增消息都触发全量重新渲染。我的解决方案：1）引入虚拟滚动，只渲染视口内的消息（约 15 条），DOM 节点减少 90%；2）Markdown 解析和代码高亮放到 Web Worker 中执行，不阻塞主线程；3）优化 Pinia 状态结构，用扁平化数据 + 计算属性，减少不必要的响应式更新。优化后，1000 条消息的对话滚动帧率稳定在 55fps 以上，输入延迟从 200ms 降到 50ms 以内，用户满意度从 60% 提升到 90%。这次性能优化也沉淀成了公司内部的 AI 对话性能最佳实践。

2. **AI 响应不稳定、格式不规范的问题如何处理？**

   - 考察点：容错设计能力
   - 回答方向：输出解析、格式校验、降级渲染、用户提示
   - 事实支撑：AI 输出不稳定是普遍问题，我们从多个层面做了容错处理：1）输出解析层：独立的解析模块，支持流式解析和完整解析，对 Markdown、JSON、代码块等格式做容错解析，比如未闭合的代码块自动补全、截断的 Markdown 尝试修复，解析成功率从 85% 提升到 98%；2）格式校验：AI 输出完成后做格式校验，如果是结构化输出（如 JSON），校验不通过则让 AI 重新生成（最多重试 2 次），减少格式错误率；3）降级渲染：如果 Markdown 解析失败，降级显示纯文本，保证内容可见；如果代码高亮失败，降级显示普通代码块，不影响阅读；4）用户提示：当检测到 AI 输出可能不完整或有问题时，在界面上显示「回答可能不完整，您可以重新生成或补充说明」，同时提供「重新生成」「继续生成」按钮；5）Prompt 工程：通过优化 System Prompt，明确要求 AI 按指定格式输出，从源头减少格式问题。经过这些处理，用户因为格式问题的投诉减少了约 70%。

3. **首屏加载慢的问题你是怎么优化的？具体优化了哪些点？**

   - 考察点：性能优化深度
   - 回答方向：代码分割、懒加载、资源预加载、CDN、缓存策略
   - 事实支撑：首屏加载优化是我主导的专项，从原来的 3.2s 优化到 1.1s，提升了约 65%。具体做了这些优化：1）代码分割：按路由做代码分割，首屏只加载首页相关代码，减少首屏 JS 体积从 1.2MB 到 350KB；2）组件懒加载：对话编辑器、代码高亮、图表等大组件用异步组件按需加载，不是首屏必需的都延后加载；3）依赖优化：ECharts 按需引入只用到的图表类型，减少 150KB；moment.js 换成 day.js，减少 200KB；4）资源预加载：使用 Preload 预加载关键字体和首屏图片，使用 Prefetch 预加载下一页可能用到的资源；5）CDN 加速：静态资源全量上 CDN，全国多节点，平均下载速度从 2MB/s 提升到 10MB/s；6）缓存策略：设置合理的 HTTP 缓存头（hash 文件名 + 长期缓存），html 不缓存，第二次访问首屏时间降到 200ms 以内；7）骨架屏：首屏显示骨架屏，减少白屏感知时间，用户主观感受更快。优化后，用户跳出率降低了 25%。

4. **不同浏览器对流式输出的兼容性问题如何处理？**

   - 考察点：兼容性处理能力
   - 回答方向：特性检测、polyfill、降级方案、统一封装
   - 事实支撑：流式输出在不同浏览器上确实有兼容性问题，主要体现在：1）Fetch streaming 支持：现代浏览器都支持，但老版本浏览器（如 Chrome < 90）不支持；2）SSE 支持：大部分浏览器支持，但某些企业浏览器或代理环境下 SSE 会被缓冲；3）ReadableStream API：老浏览器不支持。我们的处理方案：1）特性检测：页面加载时检测浏览器是否支持流式输出，不支持则自动降级；2）Polyfill：针对 ReadableStream 引入 web-streams-polyfill，补全 API，兼容到 Chrome 80+；3）降级方案：如果流式输出不可用，自动降级为普通请求 + 轮询，虽然体验差一些但功能可用，保证 100% 浏览器可用；4）统一封装：所有流式请求都走我们封装的 useStream 钩子，内部自动处理兼容性和降级，业务层不用关心，保证代码一致性；5）白名单机制：对已知有问题的浏览器或网络环境（如某些代理服务器会缓冲 SSE），直接走降级方案，避免用户遇到问题。目前流式输出的覆盖率约 95%，降级 5%。

5. **AI 对话中的安全问题你考虑了哪些？如何防止 prompt 注入？**
   - 考察点：安全意识
   - 回答方向：输入校验、内容过滤、输出审查、前后端双重校验
   - 事实支撑：AI 安全是企业级应用的红线，我参与了安全方案的设计和前端落地：1）输入侧安全：前端做输入长度限制（最多 4000 字）、特殊字符过滤、敏感词检测，防止用户输入恶意 prompt，后端也有更严格的校验，前后端双重保障；2）输出侧安全：AI 输出内容经过内容安全审查，过滤敏感、违法、违规内容，前端也有一层过滤作为兜底；3）Prompt 注入防护：前端对用户输入做转义和隔离，后端使用独立的 System Prompt 和用户输入分离，防止用户通过输入篡改系统指令，我们测试过常见的 prompt 注入攻击，防护率 95% 以上；4）数据隔离：多租户架构下，严格的数据权限控制，A 企业的知识库内容不会被 B 企业的对话引用，前端接口都带租户标识；5）操作审计：删除数据、导出知识库等敏感操作需要二次确认，并记录操作日志，便于审计；6）隐私保护：对话内容默认不用于模型训练（用户可选择是否贡献数据），敏感信息可以打码显示。上线至今未发生过安全事故。

### 产品与协作挑战

1. **AI 产品需求变化快，你如何应对频繁的需求变更？**

   - 考察点：适应能力、架构前瞻性
   - 回答方向：模块化设计、插件化架构、抽象层设计、快速迭代
   - 事实支撑：AI 产品确实迭代很快，我们平均每周都有新需求，每月都有大的功能调整。我的应对策略：1）架构上留足扩展空间：采用插件化架构，新功能做成独立插件，不影响核心代码，新增一个功能模块平均只需要 2 人天，而不是改核心代码；2）抽象层设计：把模型调用、工具调用、对话管理等核心能力抽象成独立的层和接口，上层业务不依赖具体实现，底层换模型、换供应商都不影响业务；3）快速原型验证：新需求先用最小成本做 Demo（一般 1-2 天），和产品、用户验证方向对了再投入正式开发，避免返工；4）组件库沉淀：把通用的 AI 组件（消息气泡、流式渲染器、工具调用卡片等）沉淀成组件库，新功能复用率达到 60%；5）敏捷开发流程：两周一个迭代，中间可以插入小需求，大需求走下个迭代，既保证灵活性又保证节奏。这套机制运行下来，虽然需求变化快，但项目质量和进度都可控。

2. **和产品经理在 AI 交互设计上有分歧时，你是怎么处理的？**

   - 考察点：沟通协作能力
   - 回答方向：数据驱动、用户调研、原型验证、A/B 测试
   - 事实支撑：AI 产品的交互没有标准答案，我和产品经理确实有过不少分歧，印象最深的是工具调用的展示方式。产品经理认为要完全透明，把所有技术细节都展示给用户；我认为普通用户不需要知道那么多细节，会增加认知负担。我们的解决方式：1）先放下立场，明确目标：都是为了更好的用户体验；2）用户调研：找了 10 个目标用户，分成两组，分别体验两种设计，观察他们的使用情况和反馈；3）原型验证：用高保真原型快速验证两种方案的可用性，记录完成时间、错误率、主观满意度；4）数据说话：调研结果显示，普通用户（70%）更喜欢简洁的设计，完成任务快 20%，满意度更高；而高级用户（30%）需要看到细节。最终我们采用了「渐进式披露」方案：默认简洁，想看详情可以展开，兼顾了两种用户。这个经历让我明白，有分歧很正常，关键是用数据和用户反馈说话，而不是谁声音大听谁的。

3. **项目 timeline 紧张时，你如何平衡质量和交付速度？**
   - 考察点：优先级判断、风险管理
   - 回答方向：MVP 思维、技术债务管理、分阶段交付、质量保障
   - 事实支撑：项目确实有过几次 timeline 紧张的情况，比如某次客户演示前两周，临时加了一个重要功能。我的处理原则是「速度可以快，质量底线不能丢」。具体做法：1）MVP 思维：和产品一起砍需求，只保留最核心的功能，砍掉锦上添花的部分，那次我们把需求砍了约 40%，保证核心能交付；2）分阶段交付：先交付可用版本，再迭代优化，比如演示用的版本可以有些 UI 不完美，但核心功能必须 work；3）技术债务管理：确实需要快的时候，允许临时加一些技术债务，但要记录下来，排期还债，不能让债务累积，那次我们记了 5 个技术债，迭代后两周内全部还清；4）质量底线：核心功能的单元测试和核心链路的回归测试必须做，代码评审不能省，安全和性能的底线不能破；5）透明沟通：提前和上级及产品说明取舍和风险，比如「这个时间点交付只能保证 A 功能，B 功能要延后一周，质量上我们会保证核心链路没问题，但边角可能有 Bug」，让大家有预期。到目前为止，所有承诺的 deadline 都按时交付了，且没有严重质量问题。

## 五、个人职责与贡献

### 架构设计贡献

1. **你主导的插件化前端框架具体是怎么设计的？有哪些核心机制？**

   - 考察点：架构设计能力
   - 回答方向：插件注册机制、生命周期钩子、扩展点设计、依赖注入
   - 事实支撑：插件化框架是我主导设计的，目标是让不同业务功能能独立开发、独立部署、按需加载，同时共享核心的对话能力。核心机制包括：1）插件注册机制：每个插件是一个独立的 npm 包，导出一个 install 方法，在主应用中注册，插件可以注册路由、组件、工具、Agent 等；2）生命周期钩子：插件有 beforeInstall、installed、beforeUninstall、uninstalled 等生命周期，用于初始化和清理资源；3）扩展点设计：核心模块定义扩展点（Extension Point），插件可以向扩展点注册实现，比如对话工具栏扩展点、消息渲染扩展点、工具菜单扩展点等，目前有 15 个扩展点；4）依赖注入：插件可以声明依赖其他插件或核心服务，框架自动注入，实现解耦；5）沙箱隔离：插件运行在隔离的作用域，不会污染全局，样式也做了隔离。目前平台已接入 8 个业务插件，开发一个新插件平均只需要 2 人天，开发效率提升了 3 倍。这个架构设计还在公司内部做了技术分享，被另外两个项目参考使用。

## 六、深度追问问题

### 技术深度

1. **如果让你重新设计这个项目，你会做哪些不同的选择？为什么？**

   - 考察点：反思能力、技术视野
   - 事实支撑：如果重新设计，我会做这几个调整：1）更早上 Monorepo：项目初期用的是多仓库，插件和核心是分开的，依赖管理和版本同步很麻烦，后来才迁到 Monorepo，早迁的话能节省不少时间；2）框架选型会更慎重：选 Vue 3 没错，但如果团队 React 更熟，我可能会选 React，因为 AI 前端生态 React 更丰富，很多工具和库都是 React 优先，比如 Vercel AI SDK 的 React 版本功能更全，Vue 版本有些滞后；3）服务端渲染（SSR）会更早考虑：项目初期是纯 SPA，后来发现 SEO 和首屏性能有问题，才考虑 SSR，要是一开始就用 Nuxt 或 Next，后面迁移成本更低；4）测试策略会左移：初期追求速度，测试覆盖不够，后期补测试成本很高，要是一开始就把核心模块的单元测试写好，长期来看效率更高；5）可观测性从第一天就做：监控和日志是后期才补上的，早期排查问题很痛苦，应该项目初期就把埋点、监控、日志体系搭好。这些都是踩过坑之后的反思。

2. **你觉得 AI 前端和传统前端最大的区别是什么？**

   - 考察点：领域理解深度
   - 事实支撑：做了一年多 AI 前端，我觉得和传统前端最大的区别有几点：1）不确定性：传统前端的输出是确定的，给定输入就有确定的输出；而 AI 的输出是不确定的，同样的问题可能有不同的答案，还可能出错，前端需要处理各种异常情况和边界 case，容错设计非常重要；2）流式交互：传统前端是请求-响应模式，等结果回来再展示；AI 是流式输出，边生成边展示，交互模式完全不同，对渲染性能、状态管理都是新的挑战；3）状态更复杂：传统前端的状态主要是用户操作产生的；AI 产品的状态包括模型状态、流式状态、工具调用状态、思考过程等，状态数量和复杂度都高了一个量级，状态管理架构要重新设计；4）性能关注点不同：传统前端关注首屏加载、页面切换速度；AI 产品还要关注首 Token 时间、生成速度、长对话性能等新的性能指标；5）对产品理解要求更高：AI 产品很多交互模式没有标准答案，前端工程师需要更多地参与产品设计，理解用户心理，设计出用户能理解、能信任的交互。总的来说，AI 前端对技术深度和产品思维的要求都更高。

3. **如何衡量一个 AI 产品的前端体验好坏？有哪些指标？**

   - 考察点：产品思维、数据意识
   - 事实支撑：衡量 AI 产品的前端体验，我觉得可以分三层指标：1）性能指标：首屏加载时间（<1.5s 优秀）、首 Token 时间（<1s 优秀）、Token 生成速度（>50 token/s 流畅）、长对话滚动帧率（>50fps 流畅）、交互响应延迟（<100ms），这些是基础体验；2）交互指标：对话完成率（完成对话的用户比例）、重新生成率（太高说明回答质量差）、工具调用成功率（>95% 合格）、错误率（<2% 合格）、功能使用率（各功能的使用情况），这些反映功能设计是否合理；3）体验指标：用户满意度（NPS 或问卷评分）、用户留存率（次日/7 日/30 日留存）、平均对话轮数（越多说明用户越愿意用）、用户反馈关键词分析（正面/负面）。我们项目中，我搭了一套前端监控系统，自动采集这些指标，每周出体验报告，驱动产品迭代优化。比如我们发现首 Token 时间超过 2s 时，用户流失率明显上升，于是推动后端和算法优化，把首 Token 时间从 2.5s 优化到 800ms，用户留存提升了 15%。

4. **AI 前端未来的发展趋势你怎么看？有哪些值得关注的方向？**

   - 考察点：技术视野、学习能力
   - 事实支撑：我一直在关注 AI 前端的发展，我觉得未来有几个方向值得关注：1）Agent 化的前端：从现在的「用户提问 → AI 回答」模式，进化到 AI Agent 主动帮用户完成任务，前端需要设计全新的 Agent 交互范式，比如任务规划可视化、执行过程可干预、结果可验证等；2）多模态交互：现在主要是文本对话，未来会融合语音、图像、视频等多种模态，前端需要支持多模态的输入输出，比如语音实时对话、图片理解生成、视频交互等；3）端侧 AI：随着 WebGPU 和端侧大模型的发展，越来越多的 AI 能力会放到端侧运行，比如端侧推理、端侧 Embedding、端侧 RAG，可以降低成本、保护隐私、提升速度，前端工程师需要掌握端侧模型部署和优化的技能；4）AI 生成 UI：用户用自然语言描述需求，AI 自动生成 UI 界面甚至完整应用，前端工程师的角色会从写代码转向设计系统、定义组件、验证质量；5）AI 辅助编程：Copilot 等工具已经在改变我们的开发方式，未来会更深入，从代码补全到模块生成再到完整功能开发，前端工程师要学会和 AI 协作。我个人最近在学习 WebGPU 和端侧模型部署，觉得这个方向很有潜力。

5. **这个项目的可扩展性如何？如果要支持 10 倍用户量，需要做哪些改造？**
   - 考察点：架构前瞻性、规模化思维
   - 事实支撑：目前架构支撑 5000 日活没问题，如果要支持 10 倍（5 万日活甚至更高），需要从几个层面优化：1）前端层面：a. 更多的缓存策略，比如对话列表本地缓存、知识库内容本地缓存，减少后端请求；b. 边缘计算：把一些静态计算和简单逻辑放到边缘函数，减少回源；c. CDN 优化：静态资源、甚至 API 响应都可以走 CDN 缓存；2）后端层面：a. 服务拆分：现在是单体，要拆成对话服务、知识库服务、Agent 服务等微服务，独立扩展；b. 消息队列：引入 Kafka 或 RabbitMQ 削峰填谷，应对突发流量；c. 数据库优化：分库分表、读写分离、向量数据库扩容；3）AI 层面：a. 模型层负载均衡：多供应商、多模型调度，避免单点；b. 缓存热门问答：常见问题的回答缓存起来，不用每次都生成；c. 流式输出优化：服务端流式传输优化，支持更大并发；4）运维层面：a. 完善的监控和告警；b. 自动化扩缩容；c. 多可用区部署，提高可用性。前端我有信心线性扩展，主要瓶颈在后端和大模型服务。

### 业务理解

1. **这个项目的商业价值是什么？你觉得它的护城河在哪里？**

   - 考察点：商业思维、产品理解
   - 事实支撑：从商业角度看，这个项目的价值：1）直接收入：SaaS 订阅费，按用户数收费，目前 ARR 约 500 万，增长很快；2）降本增效：客户使用后员工效率提升 40%，按 100 人企业算，每年节省人力成本几百万，客户愿意付费；3）数据沉淀：企业知识库和使用数据沉淀在平台上，形成数据壁垒，切换成本高。我觉得它的护城河有几层：1）数据护城河：企业的知识库和历史对话数据是核心资产，用得越久数据越多，效果越好，用户越离不开；2）场景护城河：我们深入了几个垂直场景（比如客服、研发、HR），做了很多场景化的 Agent 和工具，通用大模型厂商做不了这么深；3）产品体验护城河：好的 AI 产品不仅是模型，更是交互体验和工作流，我们一年多打磨出来的交互细节、性能优化、错误处理等，不是随便抄就能抄走的；4）生态护城河：插件化架构，第三方可以开发插件，形成生态，生态起来了壁垒就高了。当然最大的风险是大模型厂商自己下场做，所以我们要深耕场景，做他们做不了的深度。

2. **如果让你负责产品的下一个迭代，你会优先做什么功能？为什么？**

   - 考察点：产品思维、优先级判断
   - 事实支撑：如果让我决定下一个迭代的优先级，我会优先做「Agent 自定义编排」功能。原因：1）客户需求强：目前有 10 几个付费客户反馈，想要定制自己的 Agent 和工作流，现在都是我们帮他们做，交付成本高，做了这个功能客户可以自己配置，既能满足客户需求，又能降低交付成本；2）提升产品天花板：现在平台主要是通用助手，客户自己编排 Agent 后，可以覆盖更多场景，产品的适用范围大大扩展，客单价也能提高；3）构建生态的基础：有了编排能力，后面可以做 Agent 市场，让第三方开发者贡献 Agent，形成生态；4）技术上有沉淀：我们已经有了插件化框架和多 Agent 协作的基础，做编排功能是顺势而为，技术风险可控。当然同时我会保留一部分资源做体验优化，比如长对话性能和移动端体验。优先级判断的标准是：客户价值 + 商业价值 + 技术可行性 + 战略契合度，Agent 编排这几项得分都很高。

3. **你是如何理解用户需求的？有什么方法可以验证需求是否正确？**
   - 考察点：用户思维、验证方法
   - 事实支撑：我理解用户需求的方法是「多渠道输入 + 交叉验证」。具体来说：1）直接接触用户：我每周都会抽 2 小时看用户反馈（客服工单、应用商店评论、社群反馈），每月至少参加 2 次用户访谈，直接听用户说什么，而不是听产品转述；2）数据分析：通过埋点数据看用户的真实行为，比如哪些功能使用率高、用户在哪一步流失、常用路径是什么，数据不会骗人，很多时候用户说的和做的不一样；3）亲身体验：我自己每天都用我们的产品工作，比如写文档、查资料、做数据分析，把自己当成深度用户，能发现很多别人发现不了的问题；4）快速验证：有新想法时，我会用最快的方式做原型（1-2 天），找几个用户试用，收集反馈，验证方向对不对，而不是上来就大投入开发；5）A/B 测试：重要的功能或交互改动，做 A/B 测试，用数据说话，看哪个版本更好。我觉得做前端不能只埋头写代码，要抬头看用户，理解用户的真实痛点，才能做出好的产品。

## 七、HR/行为面试问题

1. **为什么选择做 AI 前端？这个方向最吸引你的是什么？**

   - 事实支撑：我从 2023 年开始转向 AI 前端，主要有三个原因：1）技术挑战性：AI 前端有很多新问题、新模式，比如流式交互、不确定性处理、Agent 可视化等，不像传统前端很多东西已经标准化了，我喜欢探索新领域，解决新问题；2）未来潜力：AI 是未来 10 年最大的技术趋势，前端作为人机交互的界面，会变得越来越重要，也会有很多新机会，提前布局这个方向，个人发展空间更大；3）创造价值感：AI 产品能实实在在提升用户的工作效率，看到用户用我们做的产品节省了时间、提升了效率，那种成就感很强。最吸引我的是「探索未知」的感觉 —— AI 交互还没有标准答案，大家都在同一起跑线上，我们可以参与定义下一代人机交互方式，这种参与感和创造感是传统前端没有的。我相信未来 3-5 年，前端工程师的核心能力会从「实现页面」转向「设计智能交互」，我想成为这个领域的先行者。

2. **你在这个项目中遇到的最大挫折是什么？如何克服的？**

   - 事实支撑：最大的挫折是有一次版本上线后，出现了严重的长对话性能问题，用户反馈很多，有几个客户甚至提出要退款。当时是上线的第二周，用户量上来后，长对话（500 条以上）的页面特别卡，滚动掉帧，输入延迟，甚至有些浏览器直接崩溃。问题爆发后，我压力很大，因为性能优化是我负责的，但我之前只测了 200 条以内的场景，没想到用户这么快就用到 500 条以上。我是这么克服的：1）先稳住：第一时间和客户沟通，承认问题，给出临时方案（减少历史消息数），承诺修复时间，先让客户情绪稳定下来；2）定位问题：用性能工具（Chrome DevTools Performance）分析，找出瓶颈是 DOM 节点过多和同步渲染阻塞主线程，花了 1 天时间定位清楚；3）攻坚解决：拉了两个前端同学，用了一周时间做性能优化，引入虚拟滚动、Web Worker、状态优化等方案，每天加班到很晚，周末也在调；4）验证上线：优化后做了充分的压测，1000 条消息也很流畅，然后灰度上线，逐步放量，观察数据没问题再全量；5）复盘总结：事后做了复盘，总结了性能测试规范、压测流程，避免类似问题再发生。这次挫折让我明白，做技术不能想当然，要站在用户角度考虑极端场景，也让我对性能优化有了更深的理解。

3. **你觉得自己在这个项目中最大的成长是什么？**

   - 事实支撑：最大的成长是从「只会写代码的前端工程师」变成了「能独当一面的技术负责人」。具体体现在几个方面：1）技术广度和深度：以前主要做业务开发，对架构、性能、工程化的理解都比较浅；这个项目中，我从零设计了插件化架构、做了深度性能优化、搭了工程化体系，技术上有了质的提升，尤其是 AI 前端这个新领域，我从入门到能做架构设计，进步很大；2）产品思维：以前是产品说什么就做什么，现在会主动思考「用户为什么需要这个功能」「这个设计合理吗」「有没有更好的方案」，会从产品和用户角度思考问题，而不只是实现需求；3）团队管理：以前只管好自己就行，现在要带 4 个人的团队，要分配任务、做代码评审、培养新人、协调资源，沟通和管理能力提升了很多；4）抗压能力：项目节奏快，问题多，压力大的时候也不少，慢慢学会了在压力下保持冷静，优先级排序，解决问题而不是焦虑。技术成长很重要，但更重要的是思维方式和综合能力的成长，这些是能带走的能力。

4. **如何看待加班？项目紧急时你会怎么处理？**

   - 事实支撑：我对加班的看法是「不鼓励常态化加班，但关键时刻要能顶上去」。具体来说：1）我不认为加班多就是好，常态化的加班往往是效率低、管理差的表现，应该通过提升效率、合理排期、优化流程来减少不必要的加班；2）但互联网项目难免有紧急的时候，比如客户演示前、版本上线前、出了线上问题，这时候该加还是要加，这是职业素养的体现；3）加班之后要有补偿，比如调休、弹性工作时间，不能总让员工用爱发电，我们团队是加班可以在项目不忙的时候调休，保证大家的休息；4）更重要的是找到加班的根本原因，如果是需求频繁变更导致的，就优化需求管理流程；如果是估时不准导致的，就提升估时能力；如果是人员不够导致的，就申请加人。我自己在这个项目中，平均每个月会有 3-5 天需要加班，主要是版本上线和攻克技术难题的时候，但大部分时间都能正常下班，我觉得这是比较健康的节奏。项目紧急时，我会先和团队一起评估工作量和时间点，看能不能通过调整优先级、砍非核心功能来保证交付，尽量让大家少加班；如果确实需要加班，我会带头上，和大家一起扛。

5. **离职原因是什么？下一份工作最看重什么？**

   - 事实支撑：离职的主要原因是想找一个更大的平台，在 AI 前端方向有更深入的发展。现在的公司和团队都很好，领导也很器重我，但公司规模比较小，AI 业务虽然增长快，但体量还是有限，我希望能去一个更大的平台，接触更大规模的用户量、更复杂的技术挑战、更优秀的人才，让自己成长更快。下一份工作我最看重三点：1）方向匹配度：希望继续做 AI 相关的前端工作，最好是 AI Agent、智能交互这个方向，这是我感兴趣也擅长的，希望能持续深耕；2）技术成长空间：希望团队有技术氛围，有技术牛人可以学习，有足够的技术挑战，能让我在技术上继续成长，而不是原地踏步；3）公司和团队：希望公司有清晰的商业模式和发展前景，团队氛围好，大家互相尊重、一起成长，而不是内耗严重的环境。薪资待遇当然也重要，但不是第一位的，我更看重长期的发展空间。

6. **你的职业规划是什么？短期和长期目标分别是什么？**

   - 事实支撑：我的职业规划是「技术专家路线」，在前端和 AI 结合的方向深耕。短期目标（1-2 年）：1）成为资深的 AI 前端专家，深入掌握 Agent 交互设计、端侧 AI、多模态交互等前沿技术；2）能独立负责中大型 AI 产品的前端架构设计，带领 10 人左右的前端团队；3）在公司内部或行业内有一定的技术影响力，做一些技术分享和输出。中期目标（3-5 年）：1）成为 AI 交互领域的技术专家，对下一代人机交互有自己的理解和实践；2）能主导从 0 到 1 的 AI 产品技术搭建，不仅是前端，还有整体技术方案；3）有自己的技术品牌，比如在 GitHub 有影响力的开源项目，或者在社区有一定知名度。长期目标（5 年以上）：1）探索 AI 时代前端工程师的新定位和新价值，成为这个领域的先行者；2）有机会的话，希望能打造一款有影响力的 AI 产品，用技术创造更大的价值；3）也不排除往技术管理方向发展，但前提是技术上先达到足够的高度。我觉得职业规划不是定死的，会根据实际情况调整，但大方向是明确的：在 AI 前端这条路上深耕，成为专家。

7. **你觉得自己的优点和缺点分别是什么？**

   - 事实支撑：我觉得自己主要有三个优点：1）学习能力强，对新技术有热情：AI 前端是新领域，很多东西没有现成答案，我喜欢主动学习和探索，能快速掌握新技术并用到项目中。比如 Three.js、Vercel AI SDK 这些，我都是边学边做，很快就能落地到项目里；2）责任心强，靠谱：交给我的事情我都会尽力做好，遇到问题不推诿，主动想办法解决，而不是等着别人来处理。团队同事都觉得和我合作很放心；3）有产品思维，不只是写代码：我会站在用户和产品角度思考问题，经常给产品提建议，有时候甚至会主动做 Demo 验证想法，而不只是被动接需求。缺点也很明显：1）有时候过于追求完美，对细节抠得太细，导致进度偏慢。比如做一个组件，我会想把所有边界情况都处理好，但有时候可以先上线再迭代，这点我在有意识地改进，学会「完成比完美更重要」；2）不太懂得拒绝：别人找我帮忙我一般都不会拒绝，导致有时候自己的任务被耽误，优先级管理做得不够好。现在我会先评估自己的时间和优先级，实在帮不了的会说明情况，而不是硬扛；3）公开演讲能力一般：在小团队内分享没问题，但在大场合（比如几百人的大会）会紧张，表达不够流畅，我也在有意识地锻炼，比如多争取分享机会。

8. **工作中遇到意见不合时，你是怎么处理的？请举个例子。**
   - 事实支撑：工作中有不同意见很正常，我处理的原则是「对事不对人，用数据和事实说话」。举个具体的例子：项目中我们在做知识库的检索结果展示时，和产品经理有过分歧。产品经理觉得应该一次展示 20 条结果，让用户有更多选择；我觉得 10 条就够了，太多了用户看不过来，而且加载慢。我们俩各说各的理，僵持不下。我是这么处理的：1）先冷静下来，明确我们的共同目标是提升用户体验和检索效率，不是争输赢；2）提出用数据验证，而不是凭感觉：找 10 个用户做可用性测试，分别用两种方案，记录任务完成时间、准确率、用户满意度；3）同时找行业参考：Google、Bing 等搜索引擎每页显示多少条，为什么；4）一起做测试，结果显示：10 条方案的任务完成时间快 15%，用户满意度评分更高（4.2 vs 3.6），大部分用户表示「10 条刚好，20 条看着累」；5）最终产品经理接受了 10 条的方案，我们还加了一个「每页显示数量」的设置，让用户可以自己调，兼顾了不同需求。这件事让我明白，有分歧不可怕，关键是放下立场，回到用户和数据上，找到最优解。
